# سرور پیشنهادی برای فروش اشتراک

مبنای پیشنهاد: تعداد مشتری هنوز مشخص نیست و کاربر امکان ارتقا می‌خواهد. این مشخصات، برآورد مهندسی شروع است؛ ظرفیت تضمین‌شده یا نتیجه آزمون بار روی سخت‌افزار خریداری‌شده نیست.

## پیشنهاد شروع

| بخش | پیشنهاد |
|---|---|
| پردازنده | ۸ vCPU اختصاصی یا سهم CPU تضمین‌شده؛ صرفاً عنوان «۸ هسته اشتراکی» کافی نیست |
| رم | ۳۲ گیگابایت |
| دیسک | ۲۵۰ تا ۵۰۰ گیگابایت NVMe، امکان افزایش ظرفیت |
| شبکه | پورت ۱ گیگابیت، IPv4 ثابت، سهم ترافیک و هزینه اضافه روشن |
| سیستم | Linux پشتیبانی‌شده؛ محیط staging و production همسان |
| دسترسی مدیریتی | SSH محدود، فایروال، امکان شبکه خصوصی و بازیابی از کنسول |
| پشتیبان | فضای جدا از سرور و ترجیحاً محل/حساب مستقل؛ حداقل متناسب با یک نسخه کامل و دوره نگهداری انتخابی |
| پشتیبانی | پایش شبانه‌روزی و مسئول مشخص رسیدگی به هشدارها |

هاست اشتراکی وردپرس یا کنترل‌پنل به‌تنهایی برای این معماری کافی نیست. نرم‌افزار به وب Next، API، پردازش‌های صف، PostgreSQL و Redis نیاز دارد. کلاس dedicated-vCPU برای بار پیوسته انتخاب مناسب‌تری است؛ [صفحه رسمی Hetzner](https://www.hetzner.com/cloud/) همین تفاوت منابع مشترک و اختصاصی را توضیح می‌دهد. این ارجاع انتخاب قطعی فروشنده یا تضمین امکان خرید از محل کاربر نیست.

در شروع کم‌ترافیک، سرویس‌ها می‌توانند روی همین یک سرور و در کانتینرهای جدا اجرا شوند. این طراحی یک نقطه خرابی دارد؛ افزایش رم، دسترس‌پذیری بالا ایجاد نمی‌کند. برای فروش با تعهد سخت‌گیرانهٔ تداوم سرویس، از ابتدا دیتابیس مدیریت‌شده با failover یا چند میزبان لازم است.

## مسیر رشد بدون بازنویسی

1. شروع: یک میزبان ۸/۳۲، فضای پشتیبان مستقل، دسترسی عمومی فقط از reverse proxy روی HTTPS؛ دیتابیس و Redis داخلی.
2. اولین جداسازی: PostgreSQL روی میزبان مستقل با حدود ۸ vCPU، ۳۲ GB RAM و ۵۰۰ GB NVMe؛ تنظیم connection pool و محدودیت اتصال. این اندازه نیز باید با اندازه واقعی داده بازبینی شود.
3. رشد پردازش: workerها روی یک یا چند میزبان جدا، ابتدا ۴–۸ vCPU و ۸–۱۶ GB RAM؛ تعدادشان تابع محدودیت API بازار و صف است.
4. تداوم سرویس: حداقل دو نمونه وب/API پشت load balancer، دیتابیس با failover، Redis متناسب با نیاز صف، برنامه بازیابی مستند. این مرحله هزینه مستقلی دارد.

برای Redis صف، AOF و noeviction تنظیم شوند؛ حذف خودکار کلیدها هنگام کمبود حافظه مناسب صف نیست. [راهنمای BullMQ](https://docs.bullmq.io/guide/going-to-production)

## چرا هنوز تعداد قطعی مشتری نمی‌گوییم؟

بار پایه = تعداد فروشگاه × محصولات فعال هر فروشگاه × دفعات بررسی روزانه × بازارهای فعال. مثلاً ۱۰۰ فروشگاه با ۱۰۰۰ محصول، ۴ نوبت و ۲ بازار، ۸۰۰ هزار بررسی محصول-بازار در روز می‌خواهد؛ میانگین حدود ۹٫۳ بررسی در ثانیه، پیش از محاسبه چند صفحه پاسخ، retry و اوج هم‌زمانی. این یک مثال محاسباتی است و به معنی توان فعلی سامانه یا مجاز بودن آن حجم درخواست نیست.

هر بررسی ممکن است چند پیشنهاد فروشنده ذخیره کند. اگر روزانه ۲ میلیون رکورد و اندازه مؤثر هر رکورد با index حدود ۱ تا ۳ KB باشد، رشد تقریبی ۲ تا ۶ GB در روز است؛ نگهداری خام طولانی به‌سرعت ۲۵۰ GB را پر می‌کند. این فرض باید با اندازه واقعی جدول‌ها اندازه‌گیری شود؛ retention/آرشیو و حذف داده موقت پیش‌نیاز ظرفیت‌سنجی‌اند.

برای ترب، Shop API محصولات خود فروشگاه را می‌خواند و منبع مستند رقبا نیست. محدودیت رسمی آن ۵ درخواست در ثانیه برای فروشگاه/توکن است؛ این عدد را نمی‌توان به پایش رقبا تعمیم داد. [مستندات رسمی ترب](https://github.com/torob/Torob-Sync/blob/main/shop_api.md)

## معیار ارتقا و پذیرش سرور

پیش از فروش، روی سرور انتخابی با داده مصنوعی و بدون درخواست انبوه به بازار واقعی، بار دو برابر هدف شروع بررسی شود. هدف اولیه پیشنهادی: خطا کمتر از ۱٪، زمان پاسخ p95 صفحات داده زیر ۵۰۰ms در شبکه داخلی، پایان صف پیش از نوبت بعدی، و بدون کندی محسوس ورود/داشبورد. این‌ها معیار پیشنهادی‌اند و هنوز اندازه‌گیری نشده‌اند.

CPU پایدار بالاتر از ۷۰٪، RAM بالاتر از ۷۵٪، دیسک بالاتر از ۷۰٪، رشد سن قدیمی‌ترین job یا کندی دیتابیس، محرک بررسی و ارتقا باشند. ابتدا گلوگاه اندازه‌گیری شود؛ افزودن CPU محدودیت API یا query نامناسب را حل نمی‌کند.

پشتیبان روزانهٔ میزبان به‌تنهایی کافی نیست. PostgreSQL باید نسخه سازگار و امکان بازیابی تا زمان مشخص با WAL داشته باشد؛ کلید رمزگذاری credentialها نیز جداگانه و امن نگهداری شود. هدف پیشنهادی شروع: از دست رفتن حداکثر ۱۵ دقیقه داده و بازیابی در حداکثر ۲ ساعت؛ تنها پس از تمرین موفق restore می‌توان به آن متعهد شد. [مستندات PostgreSQL](https://www.postgresql.org/docs/current/continuous-archiving.html)

محل میزبانی را پس از آزمون دسترسی از همان دیتاسنتر به سرویس‌های مجاز ترب، ملی‌پیامک و درگاه انتخاب کنید. قبل از خرید بلندمدت، یک دوره کوتاه برای شبکه، تأخیر، محدودیت حساب و دیسک کافی است. قیمت جاری و شرکت نهایی پس از مشخص شدن بودجه و دسترسی قابل خرید تعیین شوند.
